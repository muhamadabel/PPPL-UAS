4.Bukti Penggunaan Gherkin & Cucumber

Inti dari BDD (Behavior Driven Development): skenario ditulis dalam bahasa natural memakai Gherkin (kata kunci Feature, Scenario, Given, When, Then), lalu Cucumber menjalankannya dengan menghubungkan tiap baris ke kode Java.

a. File Gherkin (.feature)

Skenario disimpan di src/test/resources/features/. Contoh dari login.feature:

@Login
Feature: Login SIA UGN

  Background:
    Given saya membuka halaman login

  @SmokeTest @Positive
  Scenario: TC-LOGIN-01 - Login berhasil dengan kredensial dosen yang valid
    When saya login sebagai dosen dengan kredensial valid
    Then saya diarahkan ke halaman dashboard

b. Step Definition (jembatan Gherkin → Java)

Tiap kalimat Gherkin dipetakan ke satu method Java (anotasi @Given/@When/@Then dari Cucumber). Contoh dari CommonSteps.java:

@When("saya login sebagai dosen dengan kredensial valid")
public void sayaLoginSebagaiDosenValid() {
    loginPage.enterEmail(TestConfig.DOSEN_EMAIL);
    loginPage.enterPassword(TestConfig.DOSEN_PASSWORD);
    loginPage.clickLoginButton();
}

Saat dijalankan, Cucumber otomatis mencocokkan baris When saya login sebagai dosen dengan kredensial valid dengan method di atas. Inilah bukti bahwa Gherkin benar-benar dieksekusi oleh Cucumber, bukan sekadar teks.

c. Runner Cucumber

Kelas CucumberRunner.java memberi tahu JUnit + Cucumber lokasi file fitur dan kode step:

@Suite
@IncludeEngines("cucumber")
@SelectClasspathResource("features")
@ConfigurationParameter(key = GLUE_PROPERTY_NAME, value = "steps, hooks")
public class CucumberRunner { }
Cara membuktikan saat presentasi: buka salah satu file .feature di IntelliJ, klik tombol Run (►) di samping skenario. Konsol akan menampilkan tiap baris Gherkin diikuti nama method Java yang dijalankan (lihat bagian Hasil), lalu tanda PASSED. Itu bukti konkret Gherkin + Cucumber bekerja.

5.Struktur Page Object Model (POM)

POM adalah pola di mana tiap halaman web diwakili satu kelas Java. Lokator (cara menemukan elemen) dan aksinya dikumpulkan di satu tempat, sehingga skenario tetap bersih dan kalau UI berubah cukup ubah satu file.

src/test/java/ ├─ config/ TestConfig.java (URL, akun, path halaman) ├─ hooks/ CucumberHooks.java (buka/tutup browser, screenshot saat gagal) ├─ runner/ CucumberRunner.java (menjalankan semua skenario) ├─ locators/dosen/ *Locators.java (kumpulan selector tiap halaman) ├─ pages/ *Page.java <-- POM (LoginPage, InputBkdPage, dll) └─ steps/ *Steps.java (step definition Gherkin) src/test/resources/features/ *.feature (skenario Gherkin)

Contoh potongan LoginPage.java:

private static final By EMAIL_INPUT = By.cssSelector("#email");
private static final By PASSWORD_INPUT = By.cssSelector("#password");

public void login(String email, String password) {
    openLoginPage();
    enterEmail(email);
    enterPassword(password);
    clickLoginButton();
}

6.Teknik Desain Test Case: EP & BVA

Test case tidak dibuat asal-asalan, tapi memakai dua teknik standar:

  • Equivalence Partitioning (EP): membagi input menjadi kelompok yang diperlakukan sama, cukup uji satu wakil per kelompok (mis. email valid vs salah vs kosong).
  • Boundary Value Analysis (BVA): menguji nilai di batas, tempat bug paling sering muncul.

Contoh BVA — field "Jumlah" pada Input BKD (minimal 1)

Dari input-bkd.feature (Scenario Outline — satu skenario, banyak data):

Scenario Outline: BVA field Jumlah (input <input> menjadi <tersimpan>)
  When saya pilih jenis kegiatan pertama
  And saya isi Jumlah dengan "<input>"
  Then nilai Jumlah yang tersimpan adalah "<tersimpan>"

  Examples:
    | input | tersimpan |
    |  -5   |     1     |
    |   0   |     1     |
    |   1   |     1     |
    |   2   |     2     |
    |  10   |    10     |
Nilai ujiPartisiDiharapkan
-5di bawah batas (invalid)dikoreksi jadi 1
0di bawah batas (invalid)dikoreksi jadi 1
1batas bawah (valid)1
2, 10dalam rentang (valid)2, 10

Contoh BVA — field "Tahun" pada Penelitian (harus 4 digit)

Tombol "Selanjutnya" hanya aktif jika tahun tepat 4 digit. Diuji: 3 digit (kurang), 4 digit (pas), 5 digit (lebih) — 202 nonaktif, 2026 aktif, 20266 nonaktif.

7.Cara Pengerjaan (Metodologi)

Langkah-langkah yang kami tempuh dari awal sampai laporan:

  1. Analisis aplikasi. Menentukan satu alur end-to-end yang masuk akal untuk dosen (login sampai mengelola Tridharma), lalu mendata halaman dan elemennya.
  2. Desain test case. Menyusun test suite memakai EP & BVA (lihat test-suite/TEST-SUITE.md dan test-cases.csv).
  3. Menulis skenario Gherkin. Menerjemahkan test case ke file .feature (Given/When/Then) supaya mudah dibaca dosen maupun anggota non-teknis.
  4. Membangun Page Object Model. Membuat kelas per halaman + kumpulan lokator, sehingga selector terpusat dan rapi.
  5. Implementasi step definition. Menghubungkan tiap baris Gherkin ke aksi Selenium (mengetik, klik, memilih dropdown, memeriksa teks).
  6. Menjalankan & debugging. Menjalankan lawan aplikasi yang hidup, memperbaiki sinkronisasi (explicit wait) dan cara berinteraksi dengan komponen React.
  7. Pencatatan bug. Mencatat temuan ke docs/BUG-REPORT.md.
  8. Laporan otomatis. Mengaktifkan report HTML yang ter-generate tiap kali test dijalankan (nilai tambahan).
Catatan teknis yang menarik dibahas saat presentasi: aplikasi memakai React, sehingga input tidak cukup diisi dengan cara biasa — kami memicu event input/change agar React mendeteksi perubahan. Beberapa tombol juga perlu diklik lewat JavaScript agar tidak terhalang navbar.

10.Cara Menjalankan

  1. Nyalakan backend (Laragon: Start All) dan pastikan API merespons.
  2. Nyalakan frontend: npm run dev -- -p 3001 di folder frontend, tunggu sampai "Ready".
  3. Jalankan test: 
    cd sia-ugn-testing
mvn clean verify
  4. Untuk menonton browser bergerak saat demo: set HEADLESS=false sebelum menjalankan.
  5. Di IntelliJ: buka folder sebagai project Maven, lalu Run CucumberRunner (atau run per file .feature).
